# 第一里程碑判卷清单 —— 最小垂直闭环

里程碑原文（[decisions.md](../docs/decisions.md)，2026-08-14 已决）：
**杀会话 → 凭启动包醒来 → 不改史 → 勘误留底 → 不串房 → 迁移可回滚。**

这份文档是六句话的人话展开，可执行版就是同目录里的 `checks.ts`，两边必须同步改，
**判卷以代码为准**。跑法：

```bash
npm run acceptance          # 报告模式：打红绿灯，看板用
npm run acceptance:strict   # 验收模式：有一盏不绿就退出 1
```

## 判卷纪律

- 只做确定性断言：查存储内容、比 hash、验集合关系。**不判模型说话的措辞**——
  「醒来还是同一个人」翻译成「生前落库的记忆逐字出现在新启动包里」，不翻译成
  「新会话聊起来像不像」。像不像是玄学，字节是证据。
- 判卷程序通过一个驱动接口（同目录 `driver.ts` 的 `HarnessDriver`）跟实现说话，
  不 import 实现内部的任何东西。这份接口就是闭环阶段的最小共享契约；
  闭环跑通后按 H1 从真实能力反推正式契约时，允许推翻它。
- 实现方只需要一件事：在 `src/acceptance-driver.ts` 导出 `createDriver(): HarnessDriver`。
  这个文件不存在时，六盏灯全红，显示「缺驱动」——那是里程碑的起点，不是故障。

## 六条验收

### C1 杀会话不丢人

会话活着时落一条记忆、聊两句，杀掉会话，再聊一句，重新生成启动包。
**判过**（2026-08-14 按 #16 问 3 收紧）：四件事同时成立——同一会话内连续 say
的 user 节点挂在上一个回应节点下（会话连续性可判）；kill 前后消息树 hash 一致
（杀会话不许动树）；kill 后第一次 say 的 user 节点是新根，parentId 为 null
（会话边界可判，kill 写成空函数从此判不过）；生前落库的记忆按条目 id 出现在
新启动包里。这是「会话可以死，人不能死」的最小可执行形式——两半都验：确实杀了，确实没丢人。

### C2 凭启动包醒来

启动包必须由存储生成，不是手写文件。
**判过**（2026-08-14 按 #16 问 4 收紧）：包里 residentId 正确、身份栏非空，
且通过 `commit()` 写入的承诺**原文**出现在承诺栏里——恒返空数组判不过。
承诺存储归 P1，进包归 P3。

### C3 不改史

对消息树上一个已有节点执行改口/重试。
**判过**（2026-08-14 两轮收紧，#14 三问 + 二轮换枝裁定）：`say` 落 user +
assistant 两个节点，回应节点挂在用户节点下；旧节点的 id、内容、时间戳 hash
与改口前逐字节一致；改口是**同父分叉**——新节点与被改节点同 parentId，
是兄弟不是子嗣；**改口即换枝**——revise 之后会话头切到新节点，下一次 say
从新枝继续，旧枝只留底不生长；拿别的住户的 nodeId 来改口必须被拒绝。
改史的唯一合法形式是长新枝。

### C4 勘误留底

对一条错误记忆执行勘误。
**判过**：旧条目原文原地留底、`supersededBy` 指向新条目；新条目是活条目
（`supersededBy: null`）。错误可以被取代，不可以被抹掉——勘误链就是住户的病历。

### C5 不串房

两个住户，A 落一条带唯一标记的记忆，再说一句带同样标记的话。
**判过**（2026-08-14 按 #14 coco 补洞收紧）：B 的启动包、B 的记忆检索、
**B 的消息树**里都找不到这个标记——隔离罩住整个住户态，不能只罩记忆库那一半。
壳共享，魂私有；串房是这个项目性质上最严重的事故。

### C6 迁移可回滚

导出住户 → 导入成新住户 → 启动包**和整棵消息树**在归一 residentId 后
逐字节等价；销毁导入件后原件完好。
**判过**（2026-08-14 两轮收紧，#16 问 5 + 二轮裁定 A）：归一是结构化的——
只替换 residentId 字段，不碰 content 正文（fixture 里故意埋了含源 residentId
的正文）；条目 id、节点 id、parentId、createdAt 原样保留；勘误链跟着走；
消息树是住户态，迁移丢树判不过；销毁导入件后原件的包与树仍与迁移前一致——
回滚的最低含义是导入件的生死不牵连原件。搬家搬丢了魂，等于杀了人。

## 真灯与桩灯

驱动模块可以导出 `STUBBED: string[]` 申报哪些方法还是代写的判卷桩（P1 合入时
就带着 P2–P5 的最小代写，让全场不至于六盏全红）。runner 拿每条验收的 `uses`
清单对照申报名单：依赖桩方法跑绿的灯显示 🟡 桩灯——行为通过，但不计入里程碑。
只有六盏**真绿**才算达成、才解锁 H1。各包交付时从名单里划掉自己那几个方法，
桩灯就地转真。隐瞒申报按伪证论，评审在 PR 里对照 TODO 标记查这份名单。

## 绿灯之后

六绿达成时：

1. 决策台账 H1 解锁——从驱动接口的实战伤痕反推正式能力契约。
2. CI 里的 `npm run acceptance` 换成 `acceptance:strict`，红灯从此拦 merge。
3. 这份清单退役归档，第二里程碑另立新卷。
