## 0. 一句话

让同一位住户同时做几件互不打扰的事，而用户面前依然只有一条生命线、没有一排互不相认的聊天卡片。

v0 的形状：可开出「项目型」隔离 session，绑一个 workspace root，默认与住户级记忆和其他 scope
互不流通，跨界只走有名字、有方向、有记录的通道，关闭时留两份归档、可按同一身份重开起新一代。

**膜是手段，不是目的。** 目的是分头做事而人不被切开；膜只是让「分头」不至于变成「串味」的那层结构。
读这份图纸时若只记住「默认封闭」，就会把它实现成一个更贵的多开窗口——那正是本单要消灭的东西。

隔离单位是 **scope**，不是 viewport；一窗流不变量不受影响。

### 1.1 v0 交付什么

一种隔离形状（项目型 preset）、一层膜（默认封闭 + 三个显式原语）、一套生命周期（开／进／出／关／续）、
两份关闭归档、一张 closure card，以及导出到住户级基建时的记录形状要求。

### 1.2 v0 明确不做

- 不做除项目型以外的其他 preset 形状（话题型、对话方型、时间段型）。
- 不做 `/btw` 式窗内浮层。边界共识只记一行：浮层可对住户说话、不可对用户说话；对用户永远只有一张嘴。落点在一窗流 harness 单。
- 不做记忆合并算法。v0 只保证候选带来源、冲突并存、不静默覆盖。
- 不做跨 session 的主题召回（discovery）。v0 只有存在可知；门框不封死（§8.4）。
- 不做人格／立场隔离。人格属住户级不可分割（§4.3）。
- 不做进程隔离。
- **不预拍自动跨界阈值。** v0 不因重复次数、相关度或时长自动搬运名单外内容。Q1 的显式名单自动读入与 B3 的存在信封保留；其余跨界走带来源的显式操作，显式操作不等于每次额外弹一次确认。
- 不改 `SessionRegistry` 的容器形状。本图纸只提出它必须能表达的东西（§2.3），具体键形状由实现单从验收反推。

**代价**：v0 的用户要先学会「给任务绑一个文件夹」。绑不了文件夹的任务（纯讨论、跨仓调研）
在 v0 只能拿到上下文与工具状态的隔离，拿不到文件隔离，且系统必须明说自己没有提供它。

## 2. 模型

### 2.1 四层骨架

```
resident ──┬── scope A ── generation 1 ── session（已关，归档只读）
           │            └─ generation 2 ── session（活，重开后）
           └── scope B ── generation 1 ── session（已关，归档只读）
```

- **resident**：持久身份、人格、长期记忆、权威生命线的所有者。隔离动作永不新建、重置或切断它。
- **scope**：策略边界。一组读入／写出／工具／触达人／寿命策略，不是 allow/deny 布尔。
- **scope generation**：这个 scope 第几次开工。稳定 scope 身份与一次活化的身份必须可分别查询、
  比较与验证；重开不改变前者。不规定底层是否用复合键编码，但不得只保留一个无法拆分的临时执行 id。
- **session**：一次开工的工作现场：局部上下文、工具状态、锁、在途派发。

### 2.2 隔离单位是 scope，不是 viewport

glossary 已定：viewport 是住户 scope 的一面视野，同一 scope 下多个 viewport 共享同一份可见事实。
所以：

- 开一个隔离 session ＝ 新开一个 scope（或按同一 scopeId 重开一代），**不是**开一扇窗。
- 同一个隔离 scope 可以同时有桌面和手机两个 viewport，两边看到同一份内容。这不破隔离。
- 关掉最后一个 viewport 不等于关闭 scope；关闭 scope 是显式动作，走 §5.4 的清单。

**代价**：用户直觉里「关掉窗口＝这件事结束了」在这里不成立，界面必须把「离开」和「关闭」
做成两个不会误按的动作，否则会出现一批用户以为已关、实际还持有锁与队列席位的僵尸 scope。

### 2.3 SessionRegistry 必须能表达的东西（不定形状）

本单不改实现，只声明验收会打到的能力：

- 同一 residentId 下可同时存在多个活 scope，互不覆盖。
- 派发回执必须能归属到 `(residentId, scopeId, scopeGeneration, dispatchId)`；少任何一维，
  §5.5 的「旧代拒收」和 §5.1 的「并行互不作废」都判不过。
- 住户级不存在单一「当前 generation」；scope 换代与 viewport 换气各有自己的代际，不能互相代用。

**代价**：实现要在既有 viewport 派发上补 scope 活化归属。当前 `DispatchReceipt` 已有
`residentId / windowId / generation / dispatchId`，这里的 generation 属 viewport；本页新增的
scope 活化校验不能替换它。多 viewport 已有实现，本单不重新宣布它等待施工，也不要求两单同批改写。

## 3. 膜

### 3.1 三条底线

1. **继承不断**：session 的创建、并行、关闭、换代都不切断住户身份与住户级连续性记录的继承关系。
2. **默认封闭**：住户身份由底线一保证继承，不参加通透名单。除名单内小信息外，scope 与住户级
   记忆之间、scope 与 scope 之间，内容默认不流通。
3. **不静默覆盖**：对住户级状态的更正只允许追加勘误链。必须不可逆删除时，原值不再可查，
   但留一块不泄露被删内容的变更疤。

### 3.2 default-in 名单（Q1）

名单覆盖已批准的非身份类、稳定且住户级的小信息，例如语言习惯与已确认偏好。
住户身份继承独立成立，不能因身份未列入这张名单或 legacy 来源缺失就把住户清空。
落法：

- 名单是一份显式清单，不是一个相似度查询的结果。
- **每条带 `origin`**，指向它当初是怎么进名单的（哪次确认、哪条事件、哪次迁移映射）。
- 缺 `origin` 的 legacy 条目**不得进入名单**，也不得按时间邻近或语义相似推测一个 origin 并落盘为
  已验证。读取路径上可以算一个显式标 `inferred` 的 fallback，不落盘、不进 evidence 图。
- 名单进入 session 不需要用户按按钮，但必须在 scope 里可查：「现在有什么是自动进来的」是一次
  普通查询，不是需要翻日志的考古。

**代价**：名单是人维护的，会长歪、会过期。v0 接受这个代价，因为替代方案（让模型判断什么算
稳定小信息）会把边界交给一个没有出处的判断，而 §3.5 的单一闸口正是为了不让这种判断存在。

### 3.3 三个原语

| 原语 | 方向 | 语义 | 必带字段 |
|---|---|---|---|
| `import` | 进 | 把外部内容显式带入某个 scope | 来源身份、目标 scope、理由、`as_of`、`derived_from` |
| `promote` | 出 | 把局部结论提为住户级**候选** | 同上 + 原始证据的权威指针 |
| `annotate` | 就地 | 写不进正文、但一定与正文一起被读到的更正 | 被加注对象、加注者、时间、理由 |

三条纪律：

- **promote 的产物是候选，不是事实。** 住户层收到候选后是否成为事实，走住户层自己的流程，
  不由 scope 决定。
- **改写的逆操作不是反向改写，是加注。** 就地覆盖会留下一个完整、通顺、可读的假事实，
  比冲突更难发现——冲突至少有两个值，陈旧只有一个。
- **加注的可发现性由读取路径保证，不由写入位置保证。** 一条正确的更正躺在库里但不在故障现场
  的读取路径上，跟没有这条更正是同一个东西。

**代价**：三个原语都要求调用方在动作当刻就说清来源、目标域和理由，写起来比直接写库麻烦。
这个麻烦是有意的：省掉它就等于允许一次无出处的跨界。

### 3.4 authority 不随信息过界

从 scope A 带到 scope B 的「已批准部署」只是一条**有来源的信息**，不带来部署能力。B 要执行，
必须回到原始授权事件复核。

- scope policy 只能进一步**收权**，不能扩权。授权来源是插件契约（H1），本单不平行造第二套权限系统。
- **裁定复述义务**：跨界进来的决定，先在目标 scope 重新物化一次（谁拍的、何时、拍了什么），
  再执行。先复述后执行。
- **复述不签发授权**：物化完整也必须回到原始授权事件，核对主体、目标域、操作及当前有效性，
  再过宿主已有权限闸与 scope 收权规则；缺原件、已撤销、不适用于目标域时仍拒绝。

**代价**：复述会让跨界执行慢一拍，并且在复述不出来时会卡住一次本来能跑通的动作。这是刻意的
——复述不出来说明来源链断了，而带着断链执行正是「转抄洗白」的成因。

### 3.5 单一闸口

通透规则钉在**所有写入的必经之路上**（存储层），不在各调用点各自实现。

判据是一个数字：在各调用点自行实现的边界检查，数量为零。

**代价**：闸口会成为热路径上的一个瓶颈，也会成为单点故障。接受，因为分散实现的边界检查
在实践中等于没有边界——总有一条新加的路径忘了检查，而它的失败是静默的。

### 3.6 控制面不住在正文里

跨界意图只能住在**不可与正文混淆的 envelope** 里：带来源身份、目标 scope、理由、回执。
scope 内正文中出现的任何寻址符号一律只是内容。

否则「讨论一扇门」等价于「打开那扇门」——而这甚至不需要真的有另一个 scope 存在，
同一条流里模型自己就能长出一个假的对方。

**能被 scope 内文本改写的边界，等于没有边界。**

**代价**：envelope 是另一套需要维护的结构，且用户和住户都得学会「说到不等于做到」。
代价的另一半更贵：不做这条，整套膜可以被一句话绕过。

### 3.7 缺口与旧指令（#66 原则 14–17、20）

跨界进入的权威状态继续受现有裁定账约束。宿主在下一轮开工与裁定级动作的必经路径检查
住户裁定账的连续序号及目标 viewport 已确认位置；推送只是加速。查账失败或缺号是「未知，按缺处理」，
不能当作「没有新规矩」，也不能等缺失的模型自行发现。

替代关系必须经现有 `supersedesSeq` 等明确引用表达，不能仅因同一种 kind 的新条目出现就覆盖旧条。
明确取代后，历史原文保留，旧事件的动作资格撤销；模型入口只能拿到当前有效动作，不能靠两段
自然语言的先后顺序猜。人类来源同样适用；声称要取代却无法确定对象时保留缺口，不臆造关系。
互不替代的多条裁定仍可同时有效。消息送达、确认到哪一条、动作消费时是否有效分开记录。

**代价**：断账时沿用既有裁定级动作闸，普通动作仍按现有权限放行并记缺口；补齐后重新验权，
不自动重放旧动作。只传送可在目标域
公开的状态与引用，不借缺口检查搬运其他 scope 正文。

## 4. 身份靠 identity，不靠 role

### 4.1 为什么

定时器注入、编排注入、hook 反馈、另一个 scope 的 import——在 role 层长得一模一样，
都是「一条不是用户打的消息」。用 role 分不出来。

### 4.2 落法

- 任何写入都带 `(source, sender_id)` 一类身份元组，**不管跨不跨界**。
- 任何写出都带目标域：写的当下就说清这是给谁看的。
- 来源、证据、权威、时效四样分开存：
  - `recordedAt` ＝ 何时进库
  - `as_of` ＝ 这是哪个时刻的截面
  - `derived_from` ＝ 加工链
  - evidence 指针 ＝ 直接指原始记录
- 层级名（理解／结晶／共识）是**加工深度**的标记，不是可信度的正向指标。加工层越多，
  离原料越远。

### 4.3 人格不进隔离

隔离 scope 里的角色发言、辩论立场、临时判断可以留在局部，写出时必须标为**局部产物**，
不得 promote 成住户级立场。隔离 session 不是新人格、不是新住户、也不是后台任务。

**代价**：局部角色扮演可以发生，但必须保留局部产物身份；它不会自动成为住户的长期立场。
系统要多保存这一层来源，不能靠发言口吻推断人格已经改变。

### 4.4 生成不重置来源

模型把 handoff、摘要、召回材料、子代理报告用自己的话再说一遍，产出的消息只是
「模型说了 X」的证据，不是「X 为真」的独立一手证据。

ingestion **不得**仅因「这条消息产生于当前 scope」就把其中断言提升为一手证据。
transformation 不创造 authority。这条同时约束 scope generation（换代）与 model generation（一次生成）。

## 5. 生命周期

### 5.1 开

原子创建，五步任一步失败都不留下半个 scope 或空目录：

```
选轮 → 预览携带包 → 建 scope + working folder → 住户层登记存在 → ready
```

- 只有身份继承与隔离策略都建立成功后，scope 才能接收第一条用户输入。登记失败不得假装成功。
- 两种入口：**分出工作区**（建好后等用户第一句）；**从此重答**（仅在选中一条用户消息时可用，
  建好后把该消息作为**明确标记的 replay** 立即派发）。
- 携带包按「东西」选，不按条数选：身份与稳定设定必带；分支点原事件（含 eventId）及其直接依赖的
  上下文默认带；摘要只能作为标了 `derived_from` 的加工品**附带**，不替代原料；更早对话、附件、
  文档、记忆候选由用户勾选；授权、在途工具、锁与未选中的局部材料**不复制**。
- 携带包是分叉当刻的**冻结截面**。此后两边不同步，往来重新过膜。
- 主线状态不变：原在生成的继续生成，原 ready 的继续收消息。住户不因 branch 动作自行开口。
- 工作目录可能已存在。失败补偿只撤销本次创建的资源；不得删除用户原有目录、文件或其他 scope
  的锁。重试同一创建操作不得静默生成第二个 scope 或重放有副作用的工具。

**代价**：原子性要求创建失败时能干净回滚一个已经建出来的目录，这在宿主没有事务的文件系统上
需要显式的补偿逻辑。做不干净的后果是一地空目录，而空目录会被下一次重开误认成「上次的进度」。

### 5.2 存在可知，内容不通

隔离 scope 创建成功的同一刻：

- **前台是同步的**：同住户所有 scope 的共享状态立即显示它存在（名字、状态、来源）。
- **模型侧是异步的**：其他 scope 的模型实例在各自**下一次 dispatch** 收到一个只含存在性与来源的
  **存在信封**。信封不写进它们的本地对话，不打断它们正在进行的生成。
- 内容不过来。

**代价**：异步意味着有一段窗口期，别的 scope 的模型不知道新 scope 存在。接受，因为替代方案
（打断正在进行的生成去插入一条通知）会把「有个新房间开了」这种低价值事件提升到中断级别。

### 5.3 项目型 preset（Q3）

v0 唯一交付的隔离形状。

- 隔离 scope 可绑定一个 **workspace root**，对应用户「cd 进一个 folder」的用法。
- **只绑目录只能叫「项目默认落点」，不叫真墙。** 只有当**所有**具备文件能力的工具都由宿主强制
  workspace root、越界读写被拒**并留痕**时，这一档才可声称文件隔离。
- 未绑定目录的隔离 scope，本轮**不声称**文件隔离——系统要明说自己没提供，不能沉默。
- 进程隔离单列不做，也不做任何声称。
- 按 D10，宿主不内置或选型通用沙箱；强制边界由已接入的执行环境／插件提供。文件能力清单必须
  包括 shell、脚本及新增插件的间接文件访问，不能只检查几个名为 read/write 的工具。若其中任一
  入口不能被约束，项目型 preset 的文件 P0 不成立，应返回未就绪／阻塞，不降格为「已经隔离」。

**代价**：「所有具文件能力的工具」是一个会随插件生态增长的集合。新插件带来一个绕过 root 的
文件 API，这一档的声称当天就失效。所以验收里有一条是**能力清单必须可枚举**——枚举不出来，
就不许声称。

### 5.4 关

关闭动作至少包括：

1. 停止接新活
2. 处理或取消在途派发
3. 释放锁与占位（回合、门禁、队列席位）
4. 拒绝旧代迟到结果
5. 归档局部记录
6. 列出未决记忆候选与已发生副作用

关闭时自动生成一张用户可见的 **closure card**：完成状态、起止时间、产物权威指针、未收口项、
副作用、送达回执。它住在**住户共享状态**里，用户从一窗流界面能看见，但：

- **不写进其他 scope 的 transcript**
- **不注入其他 scope 的模型上下文**

「这几天具体做了什么」的叙事交代会泄露隔离内容，只作为该 scope 的**本地候选**；
用户明确点「带回主线」后才走 promote。**任何情况下不把隔离 transcript 倒回主线。**

**代价**：用户会看到一张信息量克制的卡片，想知道细节得点进权威指针。这是有意的——
卡片一旦开始概括内容，膜就在关闭动作上破了一个口。

### 5.5 续（Q2）

- `scopeId` 稳定。关闭后按同一 scopeId 重开，进度可续。
- 重开 **generation + 1**。
- **旧代回执一律拒收**，不是「尽量过滤」，是判定不等即丢弃并留日志。
- 住户级不存在「当前 generation」。

这里拒收的是**作为新代输入或有效动作**的资格。已经发生的工具副作用仍归旧代的机器台账，
迟到结果、无法取消或结果未知都留证，不能因拒绝消费就写成「没有发生」。

**代价**：换代边界上有些操作无法撤回，需要继续核对旧代副作用；新代不能自动重跑它们。
拒绝旧代污染与保留外部事实要同时成立。

### 5.6 切换感知（Q5：只留效果）

用户从主线切到隔离 scope（或反向）时，**能明确感知现场已变**（scope 名、目录、带入包随之改变），
同时**住户身份与对话入口保持连续**——不呈现为打开了一个新联系人或新聊天。

只保留一条画面约定：**门钉在分岔那一格**——屋里的钟停在分岔时刻（`as_of`），出门回主线永远回到
「现在」，不是回到分岔口。其余画面语言（长廊、平面图亮灯、match cut、两层 token）留在
#66 §7，本图纸不复制。

**代价**：本单只验收 D1 的效果，不验收方案本身。方案换了不算违约，效果丢了才算。

## 6. 关闭归档两份

这是 §5.4 第 5 步的展开，单列因为它最容易被做塌。

| | 机器台账 | 亲笔交接信 |
|---|---|---|
| 谁写 | 系统自动 | 住户当刻亲笔 |
| 内容 | 起止、产物指针、未收口项、副作用、回执 | 这一代做了什么、为什么这么判、还欠着什么 |
| 写不出时 | 不允许缺 | **留空** |
| 转抄 | 状态可从权威记录重建，保留来源与截面 | 不许把上一代意图改署为本代亲笔判断 |
| 继任者 | 可读 | 可读，但**不得补因果** |

**禁止继任者补因果**是这一节的核心：上一代做决定时的上下文已经死了，继任者看着结果反推原因
是真诚的，也是错的。它会产出一段读起来完全合理、且永远无法被证伪的假历史。

落法与 D8 的三档标注对齐：信里的条目按 **承诺与生效中的约束 ／ 事实与状态 ／ 判断与意图** 三档标注，
一条只装一档。继任者对第一档无权推翻（只能走正常解除流程），对第二档以现实为准，
对第三档有权不同意——**且不得续写前任对自己行为的事后分析**。

读取上一封信仍是 D8 启动包的一部分，不因「禁止转抄」被禁用；写信的是当前住户实例，
不得由脚本或另一模型冒署。机器台账另记写信成功、未及写、失败等可观察结果；正文可空，
不得把「没有写成」伪装成住户亲笔说了「本代无新增判断」。

**代价**：写不出就留空意味着会有空信。空信比脚本代写的信诚实，也比它难看。
接受难看的那一面。

## 7. 导出与合入

隔离 scope 导出到住户级基建的记录，每条必须带：

`scope` · `可见性` · `来源` · `as_of` · `derived_from` · **只指权威源的指针**

合入规则：

- **只追加，不覆盖。** 先落为候选。
- **冲突可见**：同一事实的不同值并存并标明，不静默选一个。
- **排序**：原料高于衍生，权威源高于摘要。
- **回执三态**：已合入 ／ 被拒 ／ 冲突待决。拒绝、失败、跳过或仅送达**都不得推进权威状态**。
- 拿不到权威源时，指针必须显式写「本指针指向副本，权威源未知」——让缺口继续可见，
  而不是指向另一份摘要装作有出处。
- legacy 记录的 origin 分三态：`unknown` ／ `inferred` ／ `verified`，**必须可区分**，
  不得把前两态显示为 `verified`。

合并的具体算法本轮不定，只定上述可观察行为。合入之后的召回与联想归记忆层（§8.4）。

**两种提交位置分开**：promote 成功只推进候选记录的提交位置，不自动推进「已采纳的住户事实」
位置。住户层按自己的采纳流程处理后，后者才变化；该流程的实现接缝待定，本单不定合并算法。
#66 验收 14 的「推进 head」按本页这两个
对象分别验，不能与同页验收 13 的「先是候选」互相打架。一窗流 `DeliveryReceipt.phase=delivered`
只证明主流事件已提交，不证明候选已采纳，也不证明外部送达。

**代价**：冲突并存会让住户层出现一段时间的「两个值都在」，读的人得自己看时间截面。
比静默选一个贵，也比静默选一个安全——静默选中的那个错值，没有任何信号会提醒任何人。

## 8. 边界表

### 8.1 与已进 main 的第一刀（#108）

`main` 上已经有一刀落地：`src/isolation/`（`IntentionalIsolation`、`IsolationPresenceStore`）
与 `acceptance/intentional-isolation.md`，其中 **IS-B1（可开可进）与 IS-B3（存在可知、内容不通）

那一页明确写着 B5 等 Q2、B1a 携带包与 working folder 原子创建属第二刀、B2 未声称。

本页与它的关系：

| 项 | 关系 |
|---|---|
| IS-B1 / IS-B3 两盏绿灯 | **仍然有效，本页不废止、不重判、不借用。** 新清单全红是因为它验的是更大的一圈，不是因为旧灯不算 |
| `IntentionalIsolation.create` | v0 的开工入口**扩写**这个已有 API，不另起炉灶 |
| II-F01～F08（开） | 与 IS-B1 同族：IS-B1 已证「登记失败不留活窗」，II-F 往上加携带包冻结、working folder 原子性、replay 标记、主线不受扰与仅回滚本次资源 |

**不借灯**：本清单不把 IS-B1 / IS-B3 的绿算进 v0 的任何一盏。IS-B1 证明的是「创建路径不假装成功」，
II-F 证明的是「携带包冻结且创建原子」——同族不等于同一件事。

**接缝风险**：`IntentionalIsolation` 目前是 `TurnGate` 实现，挂在 message-tree 的回合闸上。
v0 的膜要求闸在**存储写入的必经路径**（§3.5），两者不是同一个位置。实现单必须说清
回合闸与存储闸各管什么，否则会出现「回合闸放行了，写入没过膜」的静默漏洞。

### 8.2 与多 viewport（#78 / `multi-viewport.md`）

| 项 | 归谁 |
|---|---|
| `(residentId, scopeId, windowId)` 三元组与回执归属 | multi-viewport |
| 同一 scope 下多 viewport 共享可见事实 | multi-viewport（本单依赖，不验收） |
| scope 之间的可见性规则 | **本单** |
| 开窗默认 scope 不许是「全局」 | multi-viewport（本单的膜依赖它成立） |
| scope 级 generation 与旧代拒收 | **本单**（与 viewport 级换代是两件事，不得合并成一个计数器） |

**接缝风险**：viewport 换代与 scope 换代都叫 generation。实现时必须是两个字段。
合成一个的后果是「换个手机看」被当成「重开一代」，旧代拒收会把正常回执全丢掉。

### 8.3 与一窗流（#92 不变量 / #84 工程落点）

- 一窗流是**前提**：一位住户对用户只有一条持续生长的流，没有会话列表。本单依赖它，不验收它。
- 隔离不是一窗流的对立面，是它的**增量功能**。没有隔离，用户只能退回多开窗口，
  而多开窗口正是一窗流要消灭的东西。
- #84 点名的「`session.list` vs 没有会话列表」由 §5.2 回答：其他 scope 的**存在性可知、内容不通**，
  存在性以只含存在与来源的信封在下一次 dispatch 到达，**不长出第二条聊天时间线**。

### 8.4 与记忆层（#35 方向）

- 本单的边界到「把记录连同 scope、可见性、来源、时效导出，并按 §7 合入」为止。
- 合入之后怎么召回、怎么触发联想，归记忆／检索基建。
- **门框不封死**：v0 的隔离模型不得让跨 scope 的 discovery 在结构上变成不可能。逻辑上允许跨 scope
  的卡片形成关系（意外联想是产品目标），但任何 scope 实际看见的图都是**经权限裁剪的投影**：
  节点、边、聚落摘要带 scope／可见性标签，查询先过源 scope 策略再聚合，
  `quarantined` 不贡献可被猜出的主题，正文默认不流通。
- v0 只交存在可知，不交主题召回。

### 8.5 与群聊 v0（#48 / #157）

两单有相邻边界，各自验收，不把下面的相似处当作彼此通过的证据：

| 群聊单说 | 本单说 | 对齐点或区别 |
|---|---|---|
| 听见 ≠ 记账 | 默认封闭 ＋ promote 是显式动作 | 内容到达注意力，不等于进入长期记忆 |
| 三本账（房间流水／投递记录／住户记忆） | §7 的回执三态 ＋ §5.4 的两份归档 | 一条内容在不同账上的状态不得压成一个布尔 |
| 房间载荷显式声明，默认私有 | §3.6 控制面不住正文 | 目标域在动作当刻声明，不靠事后过滤 |
| 人类控制帧不排队 | §3.4 authority 不随信息过界 | 分别管调度优先级与执行权限；优先到达不等于授权有效 |

**接缝风险**：群聊的「房间」与本单的「scope」不是同一个东西——房间是多住户共享的可见性容器，
scope 是单住户内的策略边界。两边都用 `scopeId` 字段时必须能区分，否则一次群发会被当成跨 scope import。

### 8.6 与插件契约（H1）

- **授权来源是插件契约**。scope policy 只能进一步缩小能力，不平行造第二套权限系统。
- glossary 的 `verified scope` / `quarantined` / `blocked` / 升级扩权闸与本单的
  「scope 只收权不扩权」同向，术语沿用不另造。

### 8.7 与 `SessionRegistry` / 记忆库 / 素皮

本单**不改**这三处实现。§2.3 只声明验收会打到的能力，容器形状由实现单从验收反推。
素皮的 `session.list / create / history` 消费本单结论，本单不因此改动它们的形状。

## 9. 代价总账

| 决定 | 代价 |
|---|---|
| v0 只做项目型 preset | 绑不了文件夹的任务拿不到文件隔离，且系统必须明说 |
| 隔离单位是 scope 不是 viewport | 「关窗＝结束」的直觉失效，需要两个不会误按的动作 |
| default-in 名单是人维护的清单 | 会长歪、会过期；换成模型判断则边界失去出处 |
| 跨界三原语强制带来源 | 写起来麻烦；省掉就等于允许无出处跨界 |
| 裁定复述义务 | 跨界执行慢一拍，链断时会卡住一次本可跑通的动作 |
| 单一闸口 | 热路径瓶颈 + 单点故障；分散实现则等于没有边界 |
| 存在信封异步到达 | 有一段窗口期别的 scope 不知道新 scope 存在 |
| closure card 克制 | 用户想看细节得点进指针 |
| 亲笔信写不出就留空 | 会有空信，难看 |
| 冲突并存 | 住户层会有一段「两个值都在」，读的人得自己判截面 |
| 换代旧代拒收 | 长任务在重开处有一道缝，旧代在途结果被丢 |
| 不预拍自动跨界阈值 | v0 的跨界全靠手动，重复搬运的疲劳感真实存在 |

## 10. 未决与留白

以下几项**本轮不拍**，留待评测或后续单：

- 自动跨界的触发规则与阈值——需要评测与事件证据，v0 无。
- 记忆合并算法。
- 除项目型以外的 preset 形状。
- `SessionRegistry` 的最终容器形状（候选：`Map<residentId, Map<scopeId, ActiveScope>>`，
  由实现单从验收反推）。
- scope 的策略向量有哪些维度、如何配置——v0 只交项目型这一个预设值，不开配置面。
- 在场模式（用户显式声明离开后拦下会触发审批弹窗的调用）——判据只认显式声明不认静默时长，
  写出通透多一维「能不能触达人」，单列不在本单。

术语沿用 glossary 的 scopeId／viewport；本 PR 补隔离 session、scope 活化代际、携带包与关闭卡的
语义定义，不借此冻结实现字段。
