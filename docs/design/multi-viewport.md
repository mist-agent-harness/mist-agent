# 多 viewport 地基改造图纸（工单 #75）

状态：图纸草案。依据 D7（#70、#72）、D8（#73）、#66 机制层、glossary「viewport」。
本页只出设计不施工；每条决定带代价行；验收清单见 [../../acceptance/multi-viewport.md](../../acceptance/multi-viewport.md)，随本页同 PR。

## 0. 一句话

地基的核心键从「住户」变成「住户 × 窗」。连续性分两层：纵向靠交接信（D8），横向靠权威事实账（D7 第四前置）。窗可以死、可以换、可以是异源引擎，住户还是那一个。

## 1. 窗口层模型

### 1.1 标识与归属

- 一扇窗 = `(residentId, scopeId, windowId)` 三元组。`windowId` 开窗时由宿主生成（`w_` + ULID），外部不可猜。
- `scopeId` 是可见性边界（私聊、客厅、任务隔离区……），不是窗。同一 scope 的多扇窗共享同一份可见事实；跨 scope 的可见性走 #66 的边界规则，本图纸不展开。
- 住户级的东西：记忆、裁定账、生命周期。窗级的东西：会话流水、代际、在途上下文、阈值配置。

**代价**：三元组进所有派发路径，接口签名全改。窗与 scope 解耦意味着开窗必须显式给 scopeId，偷懒默认值的诱惑会一直存在——默认 scope 只能是「私聊」，不许默认「全局」。

### 1.2 open / kill 新语义

- `open(residentId, scopeId)` → 新开一扇窗，返回 `{windowId, generation: 1}`。**不再**有「重复 open 原地换代」：同一住户已有活窗时再 open 就是多开一扇，这正是 D7 的本义。
- `kill(windowId)` 幂等，窗归档为只读日志。住户级 `kill(residentId)` 保留，语义=杀掉该住户全部活窗（用于 reset/forget 入口，D7 前置②）。
- 换代（generation）是窗内概念：换气时 `generation + 1`，windowId 不变。旧语义的「重复 open 换代」由换气流程接管，见 §4。

**代价**：现 `SessionRegistry.open()` 的「不检查已有活会话」行为是被 #60 文档明确依赖过的语义，改掉它属于破坏性变更；external 前端若按旧文档写了「先 get 再 open」，新语义下依然正确（多开合法），反向兼容成立。但「一住户一活会话」的隐式假设可能藏在任何角落，验收 MV-02 专门打这个。

## 2. 代际、回执与迟到过滤下沉

- `DispatchReceipt` 从 `{residentId, generation, dispatchId}` 扩为 `{residentId, windowId, generation, dispatchId}`。
- 迟到过滤 `belongsToActiveSession` 改为窗级判定：回执的 `(windowId, generation)` 不等于该窗当前值即丢弃。**住户级不再有「当前代际」这个概念**。
- 同一住户两窗并行派发，回执各自归窗，互不丢弃。

**代价**：过滤粒度变细后，「换窗续话」场景的迟到结果会正确落入新窗而不是被误杀——这是收益。真正的代价是调试复杂度：回执链路多一层维度，日志必须打印完整三元组，否则排查噩梦。

## 3. 权威事实账与开工闸（D7 第四前置的机制落位）

### 3.1 账

- 每住户一本账：append-only，条目 `{seq, ts, author, kind, body, supersedesSeq}`，`seq` 单调递增由账侧发号。`kind ∈ {ruling, active_rule, confirmed_preference, supersede}`。`supersedesSeq` 是机器可读的指针：`kind=supersede` 的条目必填（指被解除条目的 seq），其余 kind 恒为 null——机器要读的指针就该是独立字段，body 留人读理由。
- **账上没有任何字段是可变的，变化只有追加这一种形状。**解除一条承诺不是改旧条目的标记，而是追加一条新账目（`kind=supersede`，`supersedesSeq` 指旧 seq，body 写解除理由，自带序号，走同一条缺口通道传播）——已 ack 旧条目的窗不会再拉它，就地改标记等于解除静默失踪（「送达 ≠ 仍然有效」事故形状）。
- **现行有效集是从日志推导的视图，不是账上的可变字段**：所有**事实条目**中，未被任何 supersede 条目指名的条目均属现行有效集；supersede 条目只进入全史与缺口传播，不进入现行有效集（2026-08-20 主笔定案：supersede 是变更记录不是事实；字面义下集合单调膨胀、全史会从启动包漏回新窗，与「新窗不背全史」相撞）。同一种 kind 多条并行生效是常态，supersede 精确指向单条 seq，不存在「最新一条盖掉旧条」的隐含语义；全史留作追溯，按需查询。
- 裁定只有一个入口：主线程落账这个动作（D7 补记：场可以有多个，账只有一本）。
- 每扇窗在账上有一行确认位：`(windowId, ackedSeq)`。
- **裁定级动作的定义**（闸的周长）：改变对外可见状态或不可恢复的动作——发言投递、合并、删除、花钱、部署。与原则六（权限分级，花钱/删除/部署单独批）同一圈。只有这类动作受 fail-closed 约束，普通动作不受。

### 3.2 拉式缺口信号（开工必经闸）

每扇窗每轮开工（turn 开始）前：

```
查账 → 账返回 (latestSeq, 本窗 ackedSeq)
  → latestSeq == ackedSeq：无缺口，开工
  → latestSeq > ackedSeq：拉取缺口条目 → 注入本轮上下文（标注来源档位）→ 回执 ack → 开工
  → 查账失败：返回「未知」按缺处理——裁定级动作 fail-closed，普通动作放行并在日志记缺口未知
```

- 回执：窗发 `ack(windowId, seq)` 回账；无回执=尚未知悉；回执丢失算传播机制的账，不算窗的（防「先确认再说」的伪报退化）。
- 推送降级为尽力而为：裁定落账后可以尝试推给各活窗加速，推丢了不告警不重试，正确性完全由拉保证。
- 禁用 `last_synced_at` 式时间戳当新鲜度判据（分不清「没有新东西」和「同步失败」）；只用序号差值。
- **新窗初始对齐**：开窗时账侧记 `baselineSeq = 开窗那一刻的 latestSeq`，新窗的 `ackedSeq` 从 baseline 起算——append-only 的账配 `ackedSeq=0` 会让新窗的缺口等于全史。现行有效集（而非全史）随启动包注入；开窗前已落账的裁定如需追溯，走归档查询，不走缺口通道。

**代价**：每轮开工多一次账查询（本地存储，亚毫秒级，成本可忽略）；真正的代价是 fail-closed 的误伤面——账不可用时裁定级动作全停。缓解：账是本进程内存储，不是网络服务，可用性等同于地基本身；账挂=地基挂，本来就该全停。

## 4. 换气流程（D8 落位）

### 4.1 状态机

```
running →（上下文 ≥ 阈值，账侧硬闸）→ threshold_reached
  → 当前回合跑完（容差封顶：一个回合含其工具调用，判断权在账侧）
  → writing_letter（住户亲笔写交接信，模板见 §4.2）
  → sealed（信落时间线，归档当前代际流水）
  → 新 generation 醒来，启动包注入（含交接信全文，醒来即已读）
```

- 阈值：成员配置的绝对 token 数，默认 300k；只能在窗开工时配置，临线的窗无权自调。
- `/new`、`/clear`、`/compact` 等一切手动入口映射到同一状态机的 `threshold_reached` 入口（手动即提前触发，不存在延后）。
- 猝死（进程死、未及写信）：窗流水归档可查；新代醒来只有上一封交接信 + 归档查询权，猝死窗的流水不自动注入。

### 4.2 交接信模板接口

```
letter = {
  title: string          # 必填，带可被检索的实体；时间线按标题切 chunk 做召回锚点
  state: Item[]          # 状态半：机器可生成/可转抄（做了什么、动了哪些文件、CI 状态）
  intent: Item[]         # 意图半：必须当刻亲笔（为什么选这条路、放弃了什么、我和她此刻的状态）
}
Item = { tier: 'commitment' | 'fact' | 'judgment', body: string }
```

- 三档语义（D8 补记三）：`commitment` 承诺与生效中的约束，继任者必须继承，只能按正常流程解除；`fact` 事实与状态，以现实为准可查证；`judgment` 判断与意图，继任者可不同意，不续写前任的事后分析。
- **承诺的真源是账，信是载体**：`commitment` 条目带 `ledger_seq` 指针，指回账上那条裁定，指针不复印条目正文。信封存、账还在，承诺不死；承诺被解除时账上追加 supersede 条目（§3.1），信里的旧指针指向的是「曾被 supersede 的条目」这一可查事实，两处的优先级无歧义。
- 标注单位是**条目**不是段落：一条只装一档（旦九，#66）。混档句必须拆开写。
- 信设长度上限（默认 2000 token，实现时校）；信不计入窗口阈值核算。
- 「亲笔」纪律只约束 intent 半：state 半允许脚本生成。纪律铺太宽会精确压垮它最想保护的部分（#66 issuecomment-5337771791）。

**代价**：模板越细，写信越像填表，亲笔的温度会被格式吃掉——这是真实风险，缓解靠「标题 + intent 半自由文体」：格式只管分区和标注，不规定措辞。

## 5. 与 webui 线协议的对齐

webui P0 的 `session.list / session.create / session.history` 与多活窗同向：

- `session.list` → 列出住户的窗（活窗 + 归档窗）
- `session.create` → `open(residentId, scopeId)`
- `session.history` → 窗的归档流水（只读）

差异说明（实现后回到 session-api.md §1.1 更新）：线协议的 session 概念 = 本图纸的窗；住户级概念（账、记忆）不进线协议，webui 不感知。

**代价**：线协议那边 session 一词已经写进若干文档，改名成本高、收益低——协议层保留 session 叫法，文档注明映射即可，不强求词汇统一。

## 6. 非目标

- 不做窗间实时互通（窗与窗不聊天，权威事实走账，任务上下文互不通）
- 不做跨住户的账（裁定账是住户级；系统级规矩另议）
- 不做交接信的内容压缩/摘要——信就是全文，长度上限管着
- 不动 H1 能力契约的既有接口形状（契约收口时按本图纸对齐，不是反过来）
