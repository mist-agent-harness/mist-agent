# Cloudflare Agent Memory：托管记忆服务调研与实测

> 日期：2026-08-22
> 状态：调研输入 + 一次受控实测，不是架构合同，不代表项目已作出技术选型。
> 材料：[官方文档](https://developers.cloudflare.com/agent-memory/)、
> [发布博客](https://blog.cloudflare.com/introducing-agent-memory/)（2026-04 私有 beta 宣布，
> 管线细节的主要信源）、2026-08-21 在测试命名空间上的一次活体实测。

## 1. 它是什么

托管的 agent 记忆服务。结构是 namespace 套 profile（profile 可按用户/agent/租户隔离，
首写自动创建）。四个核心操作：

- `ingest()`：投喂对话，管线自动抽取记忆（抽取、验证、分类、存储、向量化全包）；
- `remember()`：调用方明确知道要记什么时，显式写单条；
- `recall()`：按主题检索，返回合成答案 + 候选记忆列表（带分数）；
- `getSummary()`：生成该 profile 全部记忆的结构化 Markdown 摘要。

 Workers 内走 `agent_memory` binding，外部走 Cloudflare REST API。
官方给的接入姿势：recall 包成模型可调的 search 工具，ingest 挂在 harness 的
compaction / 会话结束等自然检查点，**不要每回合都 ingest**。

## 2. 管线细节（发布博客披露，值得逐条读）

**摄入管线**：消息先做内容寻址（SHA-256(session+role+content) 截 128 位），重复投喂
幂等。抽取双通道并行：全量粗抽（10K 字符分块、两条重叠、四块并发、相对日期落地成
绝对日期、带行号出处）+ 细节专抽（人名/价格/版本号这类粗抽容易丢的具体值）。
抽完过八道验证（实体同一性、时间准确性、推断是否有原文支撑等），每条记忆
通过/修正/丢弃。分类四类：facts（当前为真，带归一化 topic key）、events（带时间点）、
instructions（规程）、tasks（短期，不进向量索引只进全文）。facts/instructions 同 key
新替旧走 supersede 版本链，旧条目前向指针指向新条目，旧向量同步删除。

**检索管线**：查询分析（topic key 排序 + 全文词 + HyDE 假设性答案嵌入）与直接嵌入并行，
然后五路并行召回——全文（Porter 词干）、fact-key 精确查、原始消息全文兜底、直接向量、
HyDE 向量——RRF 融合，fact-key 权重最高，时间近者破平局。顶部候选交给合成模型生成
自然语言答案。时间计算（日期推算）走正则+算术确定性地算，不让模型碰。

**工程口径**：抽取/验证/分类/查询分析用小模型（博客点名 Llama 4 Scout 17B MoE），
只有答案合成用大模型（Nemotron 3 120B）——「只有合成这一环砸参数有稳定收益」。
存储每 profile 一个 Durable Object（SQLite）+ Vectorize 索引，隔离按 DO 天然完成。
AI 调用带 session affinity 头吃 prompt 缓存。

## 3. 实测记录（2026-08-21，测试命名空间，真实 agent 聊天记录批量投喂）

方法：自建脚本把约 1.4k 条真实对话文本（user/assistant，滤掉工具噪音）分 80 批
ingest 进同一 profile，随后用 recall 提问验证。过程零失败（ingest 幂等可重入）。

观察到的事实：

- **抽取质量好且原子化**：一段话被拆成多条独立事实并正确分类（fact/event），
  「今天」这类相对时间被落地成绝对日期。摘要接口输出可读性高。
- **消化有明显延迟**：ingest 秒回成功，但抽取/向量化在后台排队，批量投喂后数分钟内
  recall 拿不到新内容。期间 recall 返回的是「检索到 30 条候选但合成拒答」——
  候选数能当消化进度的探针用。
- **assistant 的发言同样被当事实抽取**。验证是对着对话文本核，不对着现实核。
  喂进去的语料本身必须干净。
- **中文查询的检索质量有水分**：四个已知答案的问题里一个完全召回失败、
  一个召回到过时版本（同主题新旧两段历史，新的尚未消化或未被 supersede 压住旧的）。
  英文内容、近邻主题的召回则很准。
- **wrangler OAuth token 约一小时过期**，直接拿来打 HTTP API 会中途 401。
  常驻接入要用专用 API token（最小授权），不能偷 wrangler 的。
- memories 的 list 接口对 OAuth token 授权行为不稳定（间歇 401），
  recall/ingest 稳定。beta 期的接口，别把它当监控面板的数据源。

## 4. 对 mist 的可用性判断

**当教材不当家具**。值得搬进自己管线的手法（按可直接抄的程度排）：

1. facts 带归一化 key + supersede 版本链 + 旧向量同步删除——「旧结论不作废、
   错的压着对的」这类记忆腐烂病的现成答案，与项目既有的版本链+勘误设计同构；
2. 召回多路并行 + RRF 融合，尤其 HyDE（把疑问句改写成答案形状再嵌入）——
   治「存是陈述、查是提问」的词表错位；
3. 写入时给每条记忆预生成 3-5 个检索问题，嵌在向量化正文前面；
4. 原始消息永远保留、全文兜底低权重参与召回——「可回指原文」原则的工业化形态；
5. 抽取两遍走（粗+细）+ 对原文的逐条验证——防抽取模型自由发挥；
6. 时间计算确定性化，不让模型算日期。

**哲学冲突点**：`ingest()` 的自动抽取等于第三方管线替住户决定什么值得记，
与「住户亲笔」原则顶牛。`remember()` 显式写入则无冲突。若未来采用，
自动线的产出应进草稿区，由住户裁定入正史。

beta 阶段，定价与限额未定，数据可导出（官方承诺「记忆可带走」）。
